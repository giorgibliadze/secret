# Secret Santa — ორნაბიჯიანი პირველი შესვლა

Next.js App Router, TypeScript და Tailwind CSS. მონაწილეთა ექვსი სახელი და ორგანიზატორის მიერ დადასტურებული ელფოსტა მხოლოდ სერვერულ `lib/accounts.ts`-შია. სიები ბრაუზერს არ გადაეცემა. პირადი ბმული, კოდი და ელფოსტით შედეგის გაგზავნა არ გამოიყენება.

## გაშვება

საჭიროა Node.js 24+ და npm. ლოკალურად გამოიყენება ფაილი; Vercel-ზე — Private Vercel Blob.

```sh
npm install
npm run dev
```

გახსენი http://localhost:3000. Production-ში HTTPS გამოიყენე:

```sh
npm run build
npm start
```

Vercel-ზე `VERCEL=1` ავტომატურად ირჩევს Private Blob-ს. პროექტს დაუკავშირე Private Blob store და გამოიყენე Vercel-ის ავტომატური OIDC ავტორიზაცია. `@vercel/blob` 2.9.0-ს `get`/`put`/`del` გამოძახებებში `token` ხელით არ გადაეცემა და `BLOB_READ_WRITE_TOKEN` სავალდებულო არ არის. SDK თავად ირჩევს გარემოს ავტორიზაციას. ფაილზე ჩუმი fallback არ არსებობს: ავტორიზაციის შეცდომა ახალ რაუნდს არ ქმნის. ერთი და იგივე Blob store და pathname შეინარჩუნე ყველა redeploy-ზე. Preview-ს თუ ცალკე გათამაშება სჭირდება, ცალკე Private store დაუკავშირე.

## პირველად შევდივარ

1. აირჩიე „პირველად შევდივარ“. საწყის ფორმაში მხოლოდ სახელისა და ელფოსტის ველებია.
2. „გაგრძელება“ სერვერზე ამოწმებს ზუსტად იმავე მონაწილის სახელისა და ელფოსტის წყვილს. ველების კიდეები იჭრება, სახელი NFC ფორმაში გადადის, ელფოსტა პატარა ასოებით შედარდება.
3. შეუსაბამობაზე ჩანს „სახელი და ელფოსტა არ ემთხვევა“; პაროლის ველი არ იხსნება და ერთჯერადი სესია არ გაიცემა.
4. სწორ წყვილზე, თუ პაროლი ჯერ არ არსებობს, იხსნება მეორე ნაბიჯი — „დააყენე პაროლი“ (10–128 სიმბოლო).
5. სერვერი პაროლის დაყენებას 10-წუთიან შემთხვევით ერთჯერად სესიას აბამს. იგი ცალკე HttpOnly ქუქიშია, JSON-ში კი მხოლოდ SHA-256 ჰეში, მონაწილე და ვადა ინახება. POST body-ში სახელის ან ელფოსტის გამოცვლა ანგარიშს ვერ ცვლის.
6. შენახვისას სერვერი ისევ ამოწმებს სესიას, ვადას და ანგარიშის მდგომარეობას. ერთი რიგის ატომურ ოპერაციაში ინახება scrypt ჰეში, ინდივიდუალური შემთხვევითი salt, აქტიური სტატუსი და ავტორიზაციის სესია; მონაწილეს ყველა პაროლის დასაყენებელი სესია უქმდება. შემდეგ პირდაპირ იხსნება კალათა ან უკვე შენახული შედეგი.

თუ პაროლი უკვე არსებობს, პირველი რეჟიმი ავტომატურად გადადის „შესვლაზე“. ის პაროლს არ აყენებს და ძველს არ ცვლის. ერთდროული დაჭერა, მეორე ბრაუზერში გახსნილი setup სესია ან გამოყენებული სესიის გამეორება პაროლს მეორედ ვერ შეინახავს. ვადაგასული სესიისას სახელისა და ელფოსტის შემოწმება თავიდან გაიარე. გვერდის განახლება setup ნაბიჯს თავიდან აჩვენებს; ხელახალი შემოწმება უსაფრთხოა.

## ჩვეულებრივი შესვლა და გასვლა

„შესვლა“ მოითხოვს მხოლოდ ელფოსტას და არსებულ პაროლს. არასწორ ელფოსტაზე, არააქტიურ ანგარიშსა და არასწორ პაროლზე ერთი პასუხია: „ელფოსტა ან პაროლი არასწორია“. პაროლი არ იცვლება.

პაროლები ღია ტექსტად არ ინახება. გამოიყენება scrypt (`N=32768, r=8, p=1`, 64-ბაიტიანი ჰეში) და თითოეულისთვის შემთხვევითი 16-ბაიტიანი salt. შედარება მუდმივი დროისაა; უცნობ ელფოსტაზეც სრულდება scrypt-ის იგივე გამოთვლა.

ავტორიზაციის ქუქი HttpOnly, SameSite=Strict, Path=/ და 30-დღიანია. Production-ში ორივე ქუქის აქვს Secure და `__Host-` პრეფიქსი; HTTPS აუცილებელია. პაროლის დაყენების ქუქი ავტორიზაციის ქუქისგან განცალკევებულია და კალათაზე წვდომას არ იძლევა. ნედლი ტოკენები/პაროლები ბრაუზერის storage-ში არ ინახება. „გასვლა“ მიმდინარე სესიას სერვერზეც აუქმებს და ორივე ქუქის შლის. სხვა მოწყობილობებზე ავტორიზაცია დამოუკიდებელია.

ხუთი წარუმატებელი ცდა ერთ ელფოსტაზე/წყვილზე 15 წუთით ზღუდავს ცდებს; ასევე მოქმედებს 40 წარუმატებელი ცდის საერთო 15-წუთიანი ზღვარი. ლიმიტები JSON-ში რჩება გადატვირთვის შემდეგაც. წარმატებული წყვილის შემოწმება შესაბამისი წყვილის ცდებს ასუფთავებს; პაროლით წარმატებული შესვლა — შესაბამისი login-ის ცდებს.

## JSON და არსებული მონაცემები

იგივე JSON სტრუქტურა ლოკალურად ინახება `data/secret-santa.json`-ში, Vercel-ზე კი Private Blob pathname `secret-santa/secret-santa.json`-ში: ექვსი ანგარიში, პაროლების ჰეშები და salt-ები, ავტორიზაციისა და ერთჯერადი setup სესიების ჰეშები/ვადები, მცდელობების ლიმიტები, წყვილები და გახსნის დროები. `/data/` Git-ში იგნორირებულია და `public`-ში არ მდებარეობს.

თუ მონაცემები ნამდვილად არ არსებობს (ლოკალურად `ENOENT`, Blob-ში მხოლოდ დადასტურებული 404), სერვერი იმავე რიგში ქმნის `data` საქაღალდეს და ექვს არააქტიურ ანგარიშს სერვერული კონფიგურაციიდან. პაროლები ცარიელია, განაწილება ჯერ არ არსებობს. იგივე მოთხოვნა შემდეგ ჩვეულებრივ გრძელდება. არსებული ანგარიშები თავიდან არ ივსება: შენარჩუნდება პაროლები, წყვილები და ბარათის სტატუსები. ძველ მხოლოდ სახელებზე დაფუძნებულ რაუნდს ანგარიშები ემატება მისი წყვილებისა და გახსნის დროების შეცვლის გარეშე.

ძველი პირადი გასააქტიურებელი ბმულები აღარ გამოიყენება. მათი ნარჩენი `activationHash` ველი ძველ JSON-ში შეიძლება დარჩეს; ახალი ნაკადი მას არ ამოწმებს და წარმატებული პაროლის დაყენებისას ასუფთავებს. ძველი გააქტიურების API და ბმულების გენერაციის CLI ამოღებულია. ძველი ექსპორტი `data/activation-links.txt` ახალი შესვლისთვის საჭირო აღარ არის.

ლოკალური წაკითხვა/ჩაწერა საერთო პროცესულ რიგში სრულდება: დროებითი ფაილი, sync და atomic rename. Blob ტრანზაქცია კითხულობს ახალ JSON-სა და მის ETag-ს (`get` + `useCache: false`), შემდეგ წერს `put`-ით, `access: private`, `allowOverwrite: true`, `ifMatch: ETag`. პირველი შექმნა იყენებს `allowOverwrite: false`-ს და ფიქსირებულ pathname-ს (`addRandomSuffix: false`).

ETag-ის კონფლიქტისას თავიდან სრულდება მთელი მოქმედება ახალი JSON-ით — სახელის, პაროლის არქონის, ერთჯერადი სესიისა და ლიმიტების ხელახალი შემოწმებით. ძველი JSON-ის ბრმად ხელახალი გაგზავნა არ ხდება. 20 წარუმატებელი კონკურენტული ცდის შემდეგ ბრუნდება შეცდომა და მომხმარებელს შეუძლია უსაფრთხოდ გაიმეოროს მოთხოვნა. წარუმატებელი login-ის ლიმიტებიც პირობითი ჩაწერით ინახება. ტრანზაქციის ბოლო CAS-ის წარმატებამდე არც წარმატებული ავტორიზაციის ქუქი იგზავნება.

დაზიანებული JSON, 401/403, არასწორი ტოკენი და ქსელური/ჩაწერის შეცდომები მონაცემებს არ ანულებს. `corrupt`, `read` და `write` შეცდომები უსაფრთხოდ ლოგირდება; მონაცემები, ტოკენები და ნედლი error message ლოგში არ ხვდება.

ლოკალური ფაილისთვის კვლავ გამოიყენე ერთი Node პროცესი და მუდმივი დისკი. Vercel-ის სხვადასხვა instance-ს ETag/CAS იცავს; მათი დისკი შენახვისთვის არ გამოიყენება. JSON/Blob-ის წაშლა პაროლის აღდგენის საშუალება არ არის.

## კალათა

მიმდინარე მონაწილეს სერვერი მხოლოდ ავტორიზაციის სესიიდან ადგენს. კალათაში სახელები არ ჩანს. თუ განაწილება არ არსებობს, მხოლოდ პირველ ამოღებაზე Fisher–Yates და `crypto.randomInt` ქმნის ექვსივე წყვილს. საკუთარი თავი არავის ხვდება და თითოეული მიმღები ზუსტად ერთხელ გამოიყენება.

პირველ გახსნაზე ინახება დრო და ჩანს „შენ საჩუქარს უმზადებ: [სახელი]“. ღილაკი შემდეგ აღარ ჩანს. განმეორებითი/ერთდროული დაჭერა, გვერდის განახლება, ხელახალი შესვლა და სხვა მოწყობილობა იმავე შედეგს აბრუნებს. „შედეგის დამალვა“ მხოლოდ ეკრანს ცვლის; მოწყობილობის სხვისთვის გადაცემისას გამოიყენე „გასვლა“.

API პასუხში მხოლოდ ავტორიზებული მონაწილის სახელი, გახსნის დრო და გახსნილი ბარათის მიმღების სახელია. setup ნაბიჯზე მხოლოდ შემდეგი რეჟიმი ბრუნდება; ნედლი ტოკენი მხოლოდ Set-Cookie ჰედერში გადადის. სრული სია, პაროლები, salt-ები და სხვა შედეგები არ ბრუნდება. პასუხებია `private, no-store`; POST დაცულია same-origin შემოწმებით.

ტესტები იზოლირებულ დროებით JSON-ებზე ამოწმებს პირველ მოთხოვნას ცარიელ საქაღალდეში, შეუსაბამო წყვილს, ორნაბიჯიან სესიას და მის ვადას, სხვისი მონაცემების ჩასმის მცდელობას, პაროლის მეორედ დაყენების აკრძალვას, სწორ/არასწორ შესვლას, ლიმიტებს, ძველი მონაცემების შენარჩუნებას, ექვსივე უნიკალურ მიმღებს, 60 ერთდროულ გახსნას და ახალ Node პროცესში შედეგის აღდგენას. რეალური ანგარიშები და შედეგები ტესტებში არ იცვლება.

## არსებული მონაცემების Private Blob-ში მიგრაცია

თუ Blob უკვე არსებობს, ის პრიორიტეტულია: ლოკალური ფაილი ან redeploy მას არ გადაწერს. თუ Blob ნამდვილად არ არსებობს და ლოკალური JSON ხელმისაწვდომია, იგი უცვლელი შიგთავსით გადაიტანება მხოლოდ პირობითი პირველი შექმნით. დაზიანებული ან წვდომადაკარგული ლოკალური წყარო ახალ მონაცემებს არ ქმნის.

პროექტის ლოკალური `data/secret-santa.json` Git-ში არ დაამატო. ლოკალური მიგრაციისთვის Vercel CLI-ით დაუკავშირე პროექტი და გადმოიტანე SDK-ის გარემოს პარამეტრები (`vercel link`, `vercel env pull .env.local`), შემდეგ:

```sh
npm run data:migrate
```

ეს ბრძანება `.env.local`-ს კითხულობს და მონაცემებს Private Blob-ში გადაიტანს მხოლოდ მაშინ, როცა იქ ჩანაწერი არ არსებობს. უკვე შენახული პაროლების ჰეშები/salt-ები, სესიები, წყვილები და გახსნის დროები შენარჩუნდება. სამიზნეზე წვდომის შეცდომა მიგრაციას წყვეტს. არარსებული ლოკალური წყაროც შეცდომაა — ბრძანება მიგრაციის ნაცვლად ცარიელ რაუნდს არ ქმნის. სერვერზე არსებული Blob ყოველთვის დისკზე აღმოჩენილ ასლზე პრიორიტეტულია.

მიგრაცია შეიძლება უსაფრთხო deployment build-შიც შესრულდეს, თუ პირადი წყაროს ფაილი build-ს დაცულად მიეწოდება; იგი არც Git-ში და არც `public`-ში არ უნდა მოხვდეს. მომდევნო ჩვეულებრივი deploy-ებისთვის წყაროს ფაილი საჭირო აღარ არის: აპი იმავე Private Blob-ს კითხულობს.

## Blob-ის შემოწმება

`npm test` შეიცავს SDK-ის იმიტირებულ Private Blob-ს რეალური ETag/CAS კონტრაქტით: პირველი შესვლა, პაროლის დაყენება, განმეორებითი შესვლა, კონფლიქტები სხვადასხვა instance-ს შორის, მიგრაციის ზუსტი ასლი, ლიმიტების განახლებები და ახალი deployment-ის მსგავსი ახალი service instance. ეს ტესტები არ უკავშირდება რეალურ store-ს.

რეალური Blob/redeploy შემოწმებისთვის ცალკე private verification namespace გამოიყენება; რეალურ მონაწილეებს პაროლი არ ეცვლებათ:

```sh
npm run test:blob-live -- --phase before --run unique-run-2026
# განახორციელე redeploy იმავე Private Blob store-ით
npm run test:blob-live -- --phase after --run unique-run-2026
```

Vercel build-ში ორივე ბრძანება ავტომატურ OIDC-ს იყენებს; ლოკალურად SDK-ის ავტორიზაცია CLI-ით გამართე. პირველი ეტაპი იზოლირებულ სატესტო JSON-ში გადის setup/password/login და ბარათის გახსნას; მეორე ამოწმებს შენახულ პაროლსა და ზუსტად იმავე შედეგს, შემდეგ სატესტო ჩანაწერებს პირობითად შლის. ეს შემოწმება აჩვენებს რეალურ redeploy-ს მხოლოდ მაშინ, თუ ეტაპებს შორის deployment ნამდვილად შესრულდა. ტესტური ფიქსირებული პაროლი მხოლოდ დროებითი იზოლირებული ჩანაწერისთვისაა, რეალურ ანგარიშებზე არ გამოიყენება.
