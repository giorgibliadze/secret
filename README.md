# Secret Santa — პირადი ანგარიშები და ერთი JSON საცავი

Next.js App Router, TypeScript და Tailwind CSS. კალათა მხოლოდ ავტორიზებულ მონაწილეს უჩანს; ექვსივე სახელი და დადასტურებული ელფოსტა სერვერზეა. წერილები არ იგზავნება. ყველა ანგარიშის მონაცემი, სესია, მცდელობების შეზღუდვა, განაწილება და გახსნის დრო ინახება ერთ `data/secret-santa.json` ფაილში.

## გაშვება

საჭიროა Node.js 24+, npm, **ერთი Node პროცესი და მუდმივი ჩაწერადი დისკი**.

```sh
npm install
npm run dev
```

გახსენი http://localhost:3000. Production-ში გამოიყენე HTTPS:

```sh
npm run build
npm start
```

**ჩვეულებრივ Vercel Functions-ზე ეს JSON ვერსია არ გამოდგება.** პროექტის ფაილური სისტემა მხოლოდ წასაკითხია; `/tmp` დროებითია და სხვადასხვა instance-ს საერთო ფაილი არ აქვს. Vercel-ისთვის საჭიროა საერთო ტრანზაქციული მუდმივი საცავი და შესაბამისი მიგრაცია. მხოლოდ ფაილის `/tmp`-ში გადატანა ან Git-ში დამატება პრობლემას არ აგვარებს. ოფიციალური აღწერა: https://vercel.com/docs/functions/runtimes

## ორგანიზატორი: პირადი გასააქტიურებელი ბმულები

სახელებისა და ელფოსტების შესაბამისობა ორგანიზატორის მიერ დადასტურდა. ის სერვერულ `lib/accounts.ts`-შია; საჯარო რეგისტრაცია ან სხვა მისამართის დამატების API არ არსებობს. საწყის ეკრანზე სახელებისა და მისამართების სია არ ჩანს.

ერთჯერადი მომზადება:

```sh
npm run accounts:setup
```

კომანდა არსებულ რაუნდს ამატებს ექვს მოლოდინის რეჟიმში მყოფ ანგარიშს, ქმნის ექვს 256-ბიტიან შემთხვევით ტოკენს და ბმულებს წერს **პირად** `data/activation-links.txt` ფაილში (უფლება `0600`). JSON-ში ტოკენის მხოლოდ SHA-256 ჰეში ინახება. ბმულების ტექსტური ფაილი ორგანიზატორისთვის გასაზიარებელი ექსპორტია; ანგარიშებისა და გათამაშების მდგომარეობა მხოლოდ მთავარ JSON-ში ინახება.

თუ დომენი ჯერ უცნობია, ფაილში ბმულებია `/#activate=…`. მიღებულ დომენს დაუმატე ეს ნაწილი, მაგალითად `https://your-app.example/#activate=…`. ან მომზადებისას მიუთითე უკვე ცნობილი მისამართი:

```sh
npm run accounts:setup -- --base-url https://your-app.example
```

თუ ანგარიშები უკვე მომზადებულია, კომანდა შეცდომით დასრულდება და არაფერს გადააყენებს. არსებულ ექსპორტს არ გადააწერს. არ გაუშვა ხელახლა ახალი ბმულების მისაღებად და არ წაშალო JSON: მასში ძველი წყვილები და გახსნილი ბარათებია. თითოეული ბმული გაუზიარე მხოლოდ შესაბამის მონაწილეს. ბმულები პაროლივით დაიცავი; ტექსტური ექსპორტი და JSON Git-ში არ დაამატო. `/data/` სრულად იგნორირებულია და `public`-ში არ მდებარეობს.

## პირველი გააქტიურება

მონაწილე ხსნის პირად ბმულს. ფორმაში შეჰყავს სახელი, ელფოსტა და ახალი პაროლი (10–128 სიმბოლო). სერვერი ამოწმებს ბმულის, სახელისა და ელფოსტის ერთ მონაწილესთან შესაბამისობას; ელფოსტას კიდეების გამოტოვებებს აშორებს და პატარა ასოებზე გადაჰყავს. სახელის კიდეები და Unicode ფორმა ნორმალიზდება.

ერთ რიგში შესრულებული ატომური შენახვით:

- ინახება ინდივიდუალური შემთხვევითი salt და scrypt ჰეში (`N=32768, r=8, p=1`, 64-ბაიტიანი გასაღები).
- ანგარიში აქტიურდება და გასააქტიურებელი ტოკენის ჰეში იშლება.
- იქმნება ავტორიზებული სესია.

პაროლი ღია ტექსტად არ ინახება. ერთდროულმა მოთხოვნებმა მხოლოდ ერთხელ შეიძლება გაააქტიუროს ანგარიში. გამოყენებული ბმული პაროლს ვერ ცვლის. ტოკენი URL-ის fragment-შია (`#activate=…`), ამიტომ URL-თან ერთად სერვერზე არ იგზავნება; ფორმის გაგზავნისას POST body-ში მოწმდება. წარმატების შემდეგ fragment იშლება მისამართიდან. ბმულის ვადა გამოყენებამდე არ იწურება; მომხმარებელს აღდგენის/პაროლის გადაყენების UI არ აქვს.

## შესვლა, სესია და გასვლა

შემდგომ შესვლაზე მხოლოდ ელფოსტა და პაროლია საჭირო. უცნობ ელფოსტას, გაუქტიურებელ ანგარიშსა და არასწორ პაროლს ერთი პასუხი აქვს: „ელფოსტა ან პაროლი არასწორია“. ამ დროს ანგარიშის პაროლი არ იცვლება; მოწმდება scrypt-ით და მუდმივი დროის შედარებით. უცნობ ელფოსტაზეც სრულდება იგივე ძვირი scrypt გამოთვლა.

ხუთი წარუმატებელი მცდელობა ერთ ელფოსტაზე ან გასააქტიურებელ ტოკენზე 15 წუთით ზღუდავს შემდგომ ცდებს. დამატებით მოქმედებს საერთო ზღვარი: 40 წარუმატებელი მცდელობა 15 წუთში. შეზღუდვები იმავე JSON-ში ინახება და გადატვირთვა არ აუქმებს. წარმატებული შესვლა შესაბამისი ელფოსტის მცდელობებს ასუფთავებს; საერთო დაცვა რჩება.

სესია შემთხვევითი 256-ბიტიანი ტოკენია. ბრაუზერში ის მხოლოდ HttpOnly, SameSite=Strict, Path=/ ქუქიშია, 30 დღით; production-ში ასევე Secure და `__Host-` პრეფიქსით. ამიტომ production-ს HTTPS სჭირდება. JSON-ში სესიის მხოლოდ ჰეში და ვადა ინახება. პაროლები და ტოკენები localStorage/sessionStorage-ში არ იწერება. ერთ ანგარიშს ერთდროულად მაქსიმუმ 10 მოქმედი სესია აქვს. „გასვლა“ სერვერზე აუქმებს მიმდინარე სესიას და ქუქის შლის; სხვა მოწყობილობები დამოუკიდებლად რჩება შესული.

## კალათა და არსებული შედეგების შენარჩუნება

API პიროვნებას მხოლოდ სესიიდან ადგენს: სახელის/ელფოსტის დამატება reveal მოთხოვნაში სხვის შედეგზე წვდომას არ იძლევა. ძველი სახელით შესვლის GET/POST მეთოდები ავტორიზაციის გარეშე აღარ მუშაობს.

თუ ძველ JSON-ში წყვილები ან გახსნის დროები უკვე არსებობს, ანგარიშების მომზადება მათ არ ცვლის. ასეთ მონაწილეს გააქტიურებისთანავე თავისი ძველი შედეგი გამოუჩნდება. გაუთამაშებელ რაუნდში მხოლოდ პირველ ამოღებაზე Fisher–Yates და `crypto.randomInt` ქმნის ექვსივე წყვილს; საკუთარი თავის შეხვედრისას თავიდან ირევა. ყველა მიმღები უნიკალურია. განაწილება და პირველი გახსნა ერთად ინახება.

შემდეგ ამოღების ღილაკი ქრება და ჩანს „შენ საჩუქარს უმზადებ: [სახელი]“. გვერდის განახლება, ხელახლა შესვლა და სხვა მოწყობილობიდან შესვლა იგივე შედეგს აჩვენებს. „შედეგის დამალვა“ მხოლოდ ეკრანზე მალავს შედეგს; მოწყობილობის სხვისთვის გადასაცემად გამოიყენე „გასვლა“.

## შენახვა და განთავსება

სერვერის `fs/promises` ოპერაციები ერთი პროცესის საერთო რიგში სრულდება. ყოველი ცვლილება ჯერ იმავე საქაღალდის უნიკალურ დროებით ფაილში იწერება, სინქრონიზდება და `rename`-ით ცვლის მთავარ ფაილს. ძველი v1 რაუნდი ანგარიშების დამატებისას ინარჩუნებს ფორმატს, წყვილებსა და გახსნის სტატუსებს. დაზიანებული JSON შეცდომას აბრუნებს და ჩუმად ახალ გათამაშებას არ ქმნის.

ფაილის ნებართვაა `0600`, ახლად შექმნილი საქაღალდის — `0700`. დაიცავი სარეზერვო ასლებიც. რამდენიმე პროცესისთვის/instance-სთვის რიგი საკმარისი არ არის; ასეთი გარემო ამ ვერსიისთვის არ გამოიყენო. განთავსებისას შეინარჩუნე `data/secret-santa.json`. ფაილის წაშლა ანგარიშებს, სესიებსა და შედეგებს წაშლის.

API აბრუნებს მხოლოდ მიმდინარე მონაწილის სახელს, გახსნის დროს და (გახსნის შემდეგ) მიმღების სახელს. ჰეშები, salt-ები, ელფოსტის სია, ტოკენები და სხვა წყვილები JSON პასუხებში არ ბრუნდება. სესიის ტოკენი მხოლოდ Set-Cookie ჰედერში გადაეცემა. პასუხები `private, no-store`-ია. შეცდომები, პაროლები და წყვილები არ ლოგირდება. POST მოქმედებები same-origin შემოწმებითაა დაცული; პროქსიმ უნდა შეინარჩუნოს საჯარო origin.
